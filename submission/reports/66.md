# Replicating Notion's Multi-View Databases in Obsidian: A Comparative Guide

Obsidian can now reproduce the practical core of Notion's multi-view databases — Table, Kanban, Calendar, and List — but only by choosing deliberately between a new native core engine and a thinning field of community plugins, several of which were archived in 2025. Roughly fourteen plugins and one core engine span the four view types, yet only a handful deliver Notion-grade direct manipulation without abandonment risk.

**Despite the common claim that Dataview "is the Notion replacement for Obsidian," Dataview implements only the read of CRUD** — it cannot create, update, or delete records natively — which disqualifies it as a standalone Notion analog. The durable foundation through 2027 is the official **Bases** core plugin plus **Datacore**, with specialist view plugins layered on top.

**The verdict, stated outright:** Obsidian Bases leads as the safe default, Datacore is the most capable successor engine, and the bgarciamoura Notion Bases plugin is the closest single-plugin feature clone — while Projects, DB Folder, and Database Views carry archival or lock-in risks that make them poor long-term bets.

## 1. Framework, Scope, and Methodology

Notion's defining feature is the **multi-view database**: one data source rendered simultaneously as Table, Board (Kanban), Calendar, and List, where an edit in any view writes back to shared records. The central question of this report is which Obsidian plugins reproduce that behavior, and how well.

The honest headline: **no single Obsidian plugin matches Notion's four-view parity out of the box.** The closest documented single configuration is Obsidian Bases paired with the obsidian-bases-views add-on, which together supply Table and List natively plus Board, Gantt, and Calendar through the extension — all over data stored in plain Markdown frontmatter[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

### Plugin roster

| Plugin | Primary view-types | Data model |
|---|---|---|
| Obsidian Bases (Core) | Table, List native; Board/Calendar via add-on | Markdown frontmatter |
| Dataview | Table, List rendering | Frontmatter + inline fields |
| Datacore | Table, List, partial board | Frontmatter + inline |
| Obsidian Projects | Table, Board, Calendar, Gallery | Folder notes |
| DB Folder | Table | YAML config |
| Notion Bases (bgarciamoura) | Table, Board, Calendar, Gallery | Frontmatter |
| Kanban | Board | Markdown file |
| Full Calendar | Calendar | Frontmatter / tasks |
| Prisma Calendar | Calendar | Frontmatter |
| Metadata Menu | Augments frontmatter | Frontmatter |
| Database Views (PlantBasedStudio) | Table, partial others | Proprietary `.dbview` |
| Note Database (emerging cohort) | Table, partial others | Unspecified |

### Scope

This report evaluates Obsidian plugins for their ability to replicate four named Notion views — Table, Kanban, Calendar, and List — on **desktop Obsidian** as the baseline. A plugin earns a place if it renders at least one of those views over note-derived data. Gallery is treated as a List-family variant, not a fifth axis.

Out of scope: general note-taking philosophy, and non-plugin software such as monday.com or editorial-calendar SaaS like Deelo.ai[Work with Opal, "Best marketing tools that integrate task management and calendars"](https://workwithopal.com/about/blog/best-marketing-tools-that-integrate-task-management-and-calendars/), which enter only as the Notion-equivalent benchmark.

### Evaluation rubric

Every plugin is scored against five weighted criteria:

| Criterion | Weight | What it measures |
|---|---|---|
| Four-View Coverage | 0.30 | How many of Table/Kanban/Calendar/List render natively |
| Database Behavior | 0.25 | Filter, sort, group, and — decisively — inline edit with write-back |
| Data Portability | 0.20 | Whether records survive in a host-neutral format |
| Maturity & Maintenance | 0.15 | Downloads, repo activity, beta-vs-stable |
| Usability & Performance | 0.10 | Learning curve, render speed at scale |

**Database Behavior is where the read-only/inline-editable split becomes the dominant discriminator:** a view that cannot write back is scored as a presentation layer, not a database surface. **Data Portability** treats frontmatter-backed data as more portable than data locked in plugin-specific config files. With Four-View Coverage and Database Behavior together holding 0.55 of the weight, a single-view, read-only plugin is structurally capped near a 0.45 ceiling no matter how mature or fast it is.

### Key vocabulary

- **Multi-View Database** — a single set of records rendered as multiple configurable view-types over the same underlying data.
- **Shared Data Source** — the property that every view reads and writes the same records, so an edit in the Board appears in the Table. This is the single most important discriminator in the report.
- **Frontmatter / YAML Properties** — the YAML key–value block at the top of a note (e.g., `status: doing`, `due: 2026-03-01`) that a database plugin reads.
- **Query Engine (DQL)** — a query language (e.g., Dataview) that assembles a view from matching notes, as opposed to a **GUI Database Plugin** exposing the same assembly through point-and-click configuration.
- **Inline Editing** — write-back: changing a cell updates the source note's frontmatter directly.
- **Plugin Stack** — a deliberate combination of plugins covering a capability no single plugin provides.

### The structural crux

The conceptual gap between Notion and Obsidian sits at the level of **data models**. Notion begins from a structured, schema-enforced store and exposes switchable renderings over it; Obsidian begins from plain-text files and asks plugins to impose structure after the fact. Understanding that inversion is the precondition for judging which plugins genuinely replicate a Multi-View Database and which merely imitate its surface.

A genuine multi-view database is a **conjunction**, not a menu: a plugin must supply both a Shared Data Source *and* switchable view-types over it. Failing either half demotes it from database to dashboard. The bgarciamoura Bases repository documents precisely the strong form — edits made in one view instantly appear in others because all views read and write the same Markdown frontmatter[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

### Schema enforcement vs. flexible frontmatter

| | Notion | Obsidian |
|---|---|---|
| Schema | Enforced typed properties[Dev.to, "Notion vs Obsidian: The Developer's Guide"](https://dev.to/pickuma/notion-vs-obsidian-the-developers-guide-to-knowledge-management-tools-3930) | Untyped, optional frontmatter |
| Editing | Rich typed editors (date pickers, dropdowns) free | Type layer must be supplied (e.g., Metadata Menu) |
| Relations | Native, with rollups[Dev.to, "Notion vs Obsidian: The Developer's Guide"](https://dev.to/pickuma/notion-vs-obsidian-the-developers-guide-to-knowledge-management-tools-3930) | Wikilinks in properties, no referential integrity[Start Page HQ, "Notion vs Obsidian Comparison"](https://startpagehq.com/compare/notion-vs-obsidian) |
| Storage | Cloud workspace, account required[Trendix, "Obsidian vs Notion"](https://www.trendix.tech/obsidian-vs-notion/) | Local user-owned Markdown[Trendix, "Obsidian vs Notion"](https://www.trendix.tech/obsidian-vs-notion/) |
| Portability | Locked to Notion | Survives any plugin |

The schema rigidity that gives Notion clean view-types is the same rigidity that locks its data behind Notion's keys; the frontmatter flexibility that makes Obsidian views harder to build is the same flexibility that keeps the data portable. **This is the central tradeoff of the whole comparison.** Data Portability favors Obsidian decisively, while out-of-the-box Database Behavior favors Notion just as decisively.

### Two replication routes

Obsidian plugins approach Notion parity from two directions:

| Dimension | Query Engine route | GUI Database route |
|---|---|---|
| Shared source | Frontmatter (portable) | Frontmatter or proprietary config |
| Inline editing | Historically read-only | Direct, Notion-like |
| Query power | High (DQL-style) | Moderate to high |
| Portability | Strong | Conditional on config format |
| Representative | Dataview, Datacore | DB Folder, Projects |

**Query engines maximize portability at the cost of editing; GUI plugins maximize editing at the cost (potentially) of portability.** The only way to get both is a frontmatter-first design or a Plugin Stack that pairs a portable source with a usable interface[Obsidian Forum, "Differences between database plugins"](https://forum.obsidian.md/t/what-are-the-differences-between-various-database-plugins/39406).

**Reading the matrix.** The single most decision-relevant pairing is the **Calendar cell against the Inline Edit cell**: Full Calendar and Prisma Calendar render native calendars, but only a shared-source plugin propagates a moved event back to a sibling table — a distinction invisible in the Calendar column alone.

The Database Behavior criterion splits cleanly: **Bases offers point-and-click filtering and sorting with inline editing, while Dataview requires query syntax but delivers aggregation, group-by, sums, and counts that Bases cannot match**[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2).

**Core structural claim: Four-View Coverage and shared-source editability are independent axes, and plugins that score high on one frequently score low on the other.** The survey resolves into single-purpose specialists versus shared-source generalists rather than a linear ranking.

## 3. Obsidian Bases (Core Plugin)

Obsidian Bases is the only multi-view database surface that ships inside the Obsidian application itself, which reshapes the entire comparison set. According to official documentation, it is a core plugin that lets users **view, edit, sort, and filter files and their properties in Table, Cards, List, and Map views** — all over the same frontmatter the rest of the vault uses[Obsidian, "Introduction to Bases," Obsidian Help](https://www.mintlify.com/obsidianmd/obsidian-help/bases/introduction).

### Data source model

Bases inverts Notion's container model. An Obsidian vault is treated not as isolated containers but as a single queryable space[Chugh, K., "The Architect's Guide to Obsidian Bases"](https://chughkabir.com/guide-obsidian-bases/), with the **data separated from the view definition**. The official help confirms all data lives in local Markdown files and their properties, with views described by Bases syntax saved as a `.base` file or embedded in code blocks[Obsidian Help, "Introduction to Bases"](https://obsidian.md/help/bases). Switching from Table to List or Map alters only the `.base` projection, never the notes beneath it — **the view is a lens, not a container.**

A 2026 review reports that the new **SQLite architecture eliminates the UI freezing** that plagued earlier database plugins, enabling seamless editing of tables with thousands of entries[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/).

### Supported views

The official set is **Table, Cards, List, and Map**[^15]:

- **Table** — the most production-ready surface, with documented filter/sort/edit and the SQLite performance win at scale[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/). Grouping is not surfaced in the core overview.
- **List** and **Cards** — native browse layouts (linear list and gallery grid) over the same data.
- **Map** — a spatial view, included in core where Kanban and Calendar are not.

**Board and Calendar are the conspicuous gaps.** They arrive only through the community **obsidian-bases-views** extension, which adds Board (Kanban), Gantt, and Calendar views to Bases[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views). Because that extension reads the same Bases views, the board it provides extends the Bases surface rather than forking the data.

### Shared source and portability

The defining property: storing data in plain frontmatter lets the views edit the same properties they display. The community packaging states it directly — **multiple views (table, board, gallery, calendar, timeline) share one underlying data source in Markdown frontmatter, so edits in one view instantly appear in others**[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin). This is the **two-way sync** read-only renderers cannot match.

On Data Portability, Bases earns an unambiguous pass: the `.base` file can be deleted without losing a single note, and the same frontmatter can be queried by Dataview, Datacore, or Metadata Menu in parallel.

### Strengths, weaknesses, status

| Strengths | Weaknesses |
|---|---|
| First-party maintenance, core-plugin status[Obsidian, "Introduction to Bases," Obsidian Help](https://www.mintlify.com/obsidianmd/obsidian-help/bases/introduction) | Only two of four canonical views native[Obsidian, "Introduction to Bases," Obsidian Help](https://www.mintlify.com/obsidianmd/obsidian-help/bases/introduction) |
| Portable Markdown data model, no lock-in[Obsidian Help, "Introduction to Bases"](https://obsidian.md/help/bases) | Board and Calendar depend on community extension[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) |
| Two-way sync across views[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) | Roadmap for absorbing Board/Calendar unconfirmed |
| SQLite editing at thousands of rows[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/) | |

**Synthesis: Obsidian Bases is the most portable and best-maintained multi-view surface in the comparison, but only a two-view-native one.** The paradox — the most-maintained option is also the most incomplete on view coverage — resolves through the data model: because the core ships a stable, portable frontmatter substrate, the community can layer Board and Calendar onto it without forking the data.

## 4. Dataview

Dataview is the declarative **Query Engine (DQL)** that turns a vault into a queryable store, and its defining characteristic is that it **reads data rather than writes it**. A query begins with one of four keywords — **LIST, TABLE, TASK, CALENDAR** — and that four-keyword vocabulary determines which Notion views Dataview can reproduce[blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/).

### View coverage by keyword

- **TABLE** — the most expressive read-only table in the comparison; filtering and sorting are written in a query language rather than menus. Passes filter and sort, fails inline edit (cells render read-only)[blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/)[notes-automate.com, "Dataview vs Obsidian Core Query for Dashboards"](https://notes-automate.com/posts/dataview-vs-obsidian-core-query-for-dashboards/).
- **LIST** — Dataview's most idiomatic output; a bullet list is itself Markdown. Full pass[blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/).
- **CALENDAR** — produces a calendar view but functions as a **density map** of which days carry notes, not an interactive scheduler. Present but shallow[blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/).
- **TASK** — a Dataview-specific convenience aggregating Markdown checkboxes; no exact Notion equivalent.
- **Kanban** — **fails entirely.** No BOARD keyword exists in the enumerated set[blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/).

So Dataview covers roughly **two-and-a-half of four**: Table and List at full strength, Calendar weakly, Kanban not at all.

### The read-only ceiling

Dataview's single most consequential limitation: a GitHub discussion states plainly that the plugin **solves only the "R" in CRUD** — create, update, and delete have been requested but not implemented[obsidian-dataview Discussion #748, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/748). Reads propagate across views automatically (every query re-reads the vault fresh), but **writes cannot be made inside a view at all.** This is the cleanest line separating query-driven tools from GUI database plugins, which provide direct editing similar to Notion's usability[Obsidian Forum, "Differences between database plugins"](https://forum.obsidian.md/t/what-are-the-differences-between-various-database-plugins/39406).

### Data model, maturity, and the Datacore trajectory

Dataview introduces **no proprietary file** — query text lives in ordinary code blocks, reading from frontmatter and Dataview's own inline-field syntax. This gives it the strongest Data Portability in the comparison, with one seam: a vault that encodes structure in **inline fields** (in the note body, not frontmatter) stores data where a frontmatter-oriented Bases view cannot read it.

Dataview is mature and thoroughly documented, but its development energy is shifting. Two longstanding limitations sit in its own tracker: it lacks **column-level computation** like sums (only row-level)[obsidian-dataview Issue #575, GitHub](https://github.com/blacksmithgu/obsidian-dataview/issues/575) and has **no native relations**[obsidian-dataview Discussion #1015, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/1015). Both are exactly what a rewrite would target — and **Datacore** is that successor.

### Dashboards and learning curve

A Dataview dashboard is a **reporting surface, not a control panel**: it shows open tasks or project status but cannot change them in place. Each query re-reads the vault at render time, producing a genuinely self-updating overview no static index can match — at the cost of rendering overhead that the notes-automate analysis flags for complex tables on mobile[notes-automate.com, "Dataview vs Obsidian Core Query for Dashboards"](https://notes-automate.com/posts/dataview-vs-obsidian-core-query-for-dashboards/). The pragmatic resolution is device-aware design: heavy TABLE queries on desktop, lightweight LIST queries on mobile.

**DataviewJS** recovers the missing capability — column sums, gallery approximations — but demands JavaScript fluency, making it a power-user escape hatch.

| Criterion | Dataview verdict | Basis |
|---|---|---|
| Table View | Pass (filter/sort/group, read-only) | [blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/)[notes-automate.com, "Dataview vs Obsidian Core Query for Dashboards"](https://notes-automate.com/posts/dataview-vs-obsidian-core-query-for-dashboards/) |
| Kanban View | Fail (no board keyword) | [blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/) |
| Calendar View | Weak pass (density map) | [blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/) |
| List View | Pass (native Markdown bullets) | [blacksmithgu, "Query Types — Dataview"](https://blacksmithgu.github.io/obsidian-dataview/queries/query-types/) |
| Inline Editing | Fail (R-only CRUD) | [obsidian-dataview Discussion #748, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/748) |
| Data Portability | Strong pass | frontmatter/inline |
| Formulas/Relations | Fail (JS workaround only) | [obsidian-dataview Issue #575, GitHub](https://github.com/blacksmithgu/obsidian-dataview/issues/575)[obsidian-dataview Discussion #1015, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/1015) |
| Usability | Split (powerful, not point-and-click) | [Obsidian Forum, "Differences between database plugins"](https://forum.obsidian.md/t/what-are-the-differences-between-various-database-plugins/39406)[notes-automate.com, "Dataview vs Obsidian Core Query for Dashboards"](https://notes-automate.com/posts/dataview-vs-obsidian-core-query-for-dashboards/) |

**Dataview is best understood not as a Notion database replica but as the most expressive reporting surface and the least point-and-click tool in this comparison.** It is the least future-proof of the three read-engine options, with Datacore positioned to dismantle its two defining constraints.

## 5. Datacore

Datacore is the most consequential recent development in the query-engine lineage, positioned by its author as the **successor to Dataview**. Where Dataview renders read-only tables, Datacore was rebuilt from the index upward to deliver **WYSIWYG views editable directly inside the note**, closing the single largest gap between a query engine and a true multi-view database.

**Headline verdict: Datacore is the single strongest query-engine candidate for replicating Notion's inline-editable Table behaviour, but it buys that capability with beta-stage instability and a JavaScript skill floor.**

### Architecture and performance

Datacore is a ground-up reimplementation of Dataview's indexing layer, documented as **up to 100× faster** thanks to an index that optimises many query types[Datacore documentation 2024, "Performance and Index Design"](https://github.com/blacksmithgu/datacore/blob/master/docs/docs/dataview/index.md). That speed is the mechanism behind editability: the optimised index makes a continuously re-rendering table tractable, which makes direct in-view editing practical rather than sluggish as the dataset grows.

The flagship is a **responsive, directly editable table** with a table editor "much more akin to what a user sees in Notion and Airtable"[Datacore README 2024](https://github.com/blacksmithgu/datacore/blob/master/README.md)[Obsidian Stats 2024, "Datacore Plugin Profile"](https://www.obsidianstats.com/plugins/datacore). **This is the first query engine in the survey to earn a clear pass on in-view direct editing.**

### View coverage

- **Table** — native, directly editable, the one view the roadmap marks complete[blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md).
- **List** — native and interactive; lists can carry buttons and stateful controls via Preact[Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views), a step above Dataview's static bullets.
- **Kanban** — **not native.** A Card view is on the roadmap[blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md); today a board requires hand-built JSX.
- **Calendar** — **not native** and not on the roadmap; buildable through the JavaScript API's time-based elements[Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views) but not shipped.

### The JSX requirement

The feature making Datacore a credible Notion substitute is the same one narrowing its audience. Views render through **Preact**, giving them internal state and live updating — but arbitrary interactivity (buttons, custom CSS, stateful controls) presupposes **JSX fluency**[Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views). The shared, editable source and the code-fluency requirement are two faces of one design choice.

### Portability and maturity

Datacore queries live in **Markdown code blocks** — portable as text, but inert without the Datacore runtime to execute them. So source data is fully portable; the rendered view is not. Maturity is a **conditional pass**: a transparent, active roadmap[blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md) signals direction, but Table is checked while Card and Grouped remain open, and beta-stage API instability means custom JSX views may need refactoring as the API stabilises.

| Dimension | Datacore verdict | Basis |
|---|---|---|
| Table view | Native, directly editable | [Datacore README 2024](https://github.com/blacksmithgu/datacore/blob/master/README.md) |
| List view | Native, interactive | [Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views) |
| Kanban view | Not native; planned Card view | [blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md) |
| Calendar view | Not native; JSX-buildable | [Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views) |
| Data Portability | Pass on data; partial on view | [Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views) |
| Maturity | Conditional pass; beta | [blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md) |
| Usability & Performance | Performance pass; usability partial | [Datacore documentation 2024, "Performance and Index Design"](https://github.com/blacksmithgu/datacore/blob/master/docs/docs/dataview/index.md)[Datacore code views documentation 2024](https://blacksmithgu.github.io/datacore/code-views) |

**Datacore is not merely a faster Dataview but a structurally different tool: by rebuilding the index for the up-to-100× speed gain and routing rendering through Preact, it converts the query engine from a read-only reporter into an editable front end.** The paradox — the most powerful query engine is also the least finished — resolves because the rebuild reset the feature-completeness clock even as it raised the ceiling. For users already fluent in query-driven views, it offers the clearest upgrade path; Kanban and Calendar are left to a Plugin Stack.

## 6. Obsidian Projects

Obsidian Projects is the clearest **no-code** answer to Notion's multi-view database, turning any folder of notes into a visual dashboard with **Table, Board, Calendar, and Gallery views, no code required**[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/). It is faster to set up than Dataview for visual project management but **less flexible for complex queries** — the two tools complement each other[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/).

### Four no-code views over a folder

Projects treats a **folder as the unit** of a multi-view database. Each note becomes a row in the Table, a card in the Board (grouped by a chosen property), a dated entry in the Calendar, or a tile in the Gallery — all reading the **same folder**[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/). This folder-as-dashboard model is a genuine **Shared Data Source**: the four views are not separate stores but four renderings of one folder.

Crucially, the **Board draws cards from the same folder that feeds the Table** — unlike the standalone Kanban plugin, whose board is its own document. A card moved on the Projects board is a note that also appears in the Table, Calendar, and Gallery.

### Portability and the maintenance question

Projects stores data in **plain Markdown frontmatter** under the banner "Plain text project planning in Obsidian"[marcusolsson/obsidian-projects, README, GitHub](https://github.com/marcusolsson/obsidian-projects/blob/5a1a7a84/README.md) — an unambiguous Data Portability pass. But the **maintenance picture is the decisive caveat**: the official obsmd-projects repository is **archived**, with its last prerelease (0.0.0-1004) dated February 12, 2025[obsmd-projects/obsidian-projects, GitHub archived](https://github.com/obsmd-projects/obsidian-projects). The community has noted it still needs a maintainer[Obsidian Forum, "Development for Projects plugin needed"](https://forum.obsidian.md/t/development-for-projects-plugin-needed/101089).

At least two genuine forks carry it forward:
- **ParkPavel's obs-projects-plus** — actively maintained at version 3.1.0[ParkPavel/obs-projects-plus, GitHub](https://github.com/ParkPavel/obs-projects-plus/blob/main/README-EN.md)
- **Acylation's obsidian-projects** — commits through October 30, 2025[Acylation/obsidian-projects, GitHub](https://github.com/Acylation/obsidian-projects)

A namesake trap: **wanadev/obsidian-project (v5.1.0) is an unrelated library, not a fork**[wanadev/obsidian-project, GitHub](https://github.com/wanadev/obsidian-project) — its healthy release history can mislead.

**The portability decouples two risk layers.** Because data is plain frontmatter, a user whose chosen fork stalls **loses only the view-rendering layer, not the underlying notes.** The worst case is re-creating view configs in a different fork, not data loss — a direct consequence of the plain-text model.

### Strengths and weaknesses

| Strengths | Weaknesses |
|---|---|
| No-code four-view coverage[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Original repo archived; bet on a fork[obsmd-projects/obsidian-projects, GitHub archived](https://github.com/obsmd-projects/obsidian-projects) |
| Plain-text frontmatter portability[marcusolsson/obsidian-projects, README, GitHub](https://github.com/marcusolsson/obsidian-projects/blob/5a1a7a84/README.md) | No cross-table calculations[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) |
| Shared folder source across views[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Advanced board features (swimlanes, WIP limits) undocumented |

**Projects occupies a defensible niche: the no-code, folder-backed, plain-text four-view dashboard, strongest on setup speed and portability, weakest on query power and maintenance governance.** Practical guidance for a 2026 adoption: install a maintained fork and track its release cadence, not the archived original.

## 7. DB Folder

DB Folder is one of the earliest community plugins to deliver a genuinely Notion-style experience: it reads a **YAML configuration stored inside a Markdown file** and renders a React DOM, supporting Notion-like features such as **formulas** and multiple data sources including folders, tags, links, and Dataview["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/).

### What it delivers

- **Table** — its flagship and strongest surface: a configurable, formula-capable grid mapping columns to frontmatter values. Clear pass on Four-View Coverage["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/).
- **Kanban / Calendar / List** — **not native.** A board requires pairing with the Kanban plugin[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6); a calendar requires Full Calendar[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar); lists fall back to a plain Dataview query — each a two-plugin arrangement rather than a view-switch over one source.

DB Folder documents no **cross-view Shared Data Source** of the kind Bases provides. Its single YAML-configured view is its own shared surface, but it is a single excellent table, not a multi-view database.

### The fifty-file scaling limit

The most concrete operational fact: users report on the plugin's own GitHub discussions that **once a folder exceeds fifty files, the table takes ages to render**[obsidian-db-folder Discussion #1067, GitHub](https://github.com/RafaelGB/obsidian-db-folder/discussions/1067). This bounds the practical folder size and is the decisive Usability & Performance data point — comfortable at small scale, failing the responsiveness bar at larger counts.

Importantly, this is a **rendering cost, not a data-integrity concern**: the YAML-in-Markdown model means a slow folder does not endanger the underlying notes. Users reconcile it by **scoping DB Folder to focused per-project folders** rather than whole-vault ones.

### Portability and verdict

DB Folder's portability is a genuine strength: the **YAML view config lives in plain Markdown**, inspectable and versionable, with notes remaining ordinary Markdown["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/). Migration to Bases means rebuilding the YAML config, not rescuing data.

| Dimension | DB Folder verdict | Basis |
|---|---|---|
| Table view-type | Strong native grid with formulas | ["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/) |
| Kanban / Calendar | No native; pair with other plugins | ["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/)[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6)[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) |
| List view-type | Partial; via Dataview list | ["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/) |
| Shared Data Source | Single-view only; no cross-view sync | ["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/)[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) |
| Portability | Strong; YAML-in-Markdown | ["About — Database Folder," obsidian-db-folder docs](https://rafaelgb.github.io/obsidian-db-folder/about/) |

**DB Folder is a single-view excellence case rather than a four-view contender** — a deep but narrow predecessor whose value is real, portable, and bounded by the fifty-file ceiling.

## 8. Notion Bases (bgarciamoura Plugin)

Notion Bases markets itself as **"the database plugin Obsidian is missing"**["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/) and front-loads the broadest advertised scope in the survey: **seven view-types, 17–18 typed column types, formulas, relations, and rollups** — all "powered by plain Markdown"["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/).

> **Naming caution:** "Notion Bases" (this community plugin) is distinct from "Obsidian Bases" (the core plugin in §3). Core Bases ships Table and List natively["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/); this plugin advertises a wider set.

### The feature matrix

The seven views are **Table, Board/Kanban, Gallery, List, Calendar, Timeline/Gantt, and Chart**["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/), covering all four Notion-canonical renderings:

- **Table** paired with **18 column types and formulas** — a spreadsheet-grade grid, a more ambitious specification than core Bases publishes["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/)["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/).
- **Board** as a property-grouped lens over frontmatter, so moving a card conceptually rewrites a property value rather than relocating text.
- **Calendar + Timeline/Gantt** from one specification — one of few tools advertising both["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/).
- **List + Gallery** as the two lighter browse renderings.

The **relations-and-rollups** layer["Relations & rollups," Notion Help Center](https://www.notion.com/help/relations-and-rollups) is the nearest any single plugin comes to reproducing Notion's linked-database behaviour from one install.

### Portability and the evidence gap

The structural premise is that all seven views are powered by plain Markdown["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/), placing records in portable frontmatter — a strong Data Portability claim, confirmed by the sibling Obsidian Bases architecture[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin). **One honest boundary:** the cited material does not state how the view definitions themselves are persisted, so the cleanest claim is that **record data is portable Markdown while the view-configuration format is unspecified.**

**The plugin's weakest axis is maturity.** The evidence confirms a live repository and a polished documentation site, but supplies **no install counts, no star totals, no release-status label.** A small but real signal of settling specs: the docs site advertises 18 column types while the repository lists 17. And the cross-view edit-propagation guarantee is best read as a **design-family inference** from the sibling Bases architecture, not an explicitly published promise.

| Axis | Notion Bases verdict | Basis |
|---|---|---|
| Table View | Pass — typed-column grid + formulas | ["Notion Bases" project documentation site](https://bgarciamoura.github.io/obsidian-notion-bases-plugin/) |

**Notion Bases is the survey's clearest case of a plugin whose advertised capability and demonstrated track record diverge.** It buys the widest multi-view breadth with genuine plain-Markdown portability, and pays with an unproven adoption record. **The single highest-value diligence step is to check the repository's recent commit activity before committing a large vault.** For a user who needs only Table and List, core Obsidian Bases (§3) remains the safer default; the unsettled open question is at what folder size a file-per-record model begins to degrade render performance.

## 9. Kanban Plugin

The Kanban plugin is the single most-downloaded dedicated view-type tool in the comparison — **913,152 downloads**[dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011) — and its philosophy diverges sharply from the multi-view ambitions elsewhere. It is documented purely as a **board tool**: Markdown-backed, drag-and-drop, with customizable columns and cards sourced from Markdown notes[dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011).

### The board, and only the board

- **Kanban** — the home axis and a strong pass: a polished drag-and-drop board for managing tasks as cards[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), with **column position as the status dimension**.
- **Table / Calendar / List** — **none documented.** Calendar functionality in the documented workflow comes from **pairing with a separate Full Calendar plugin**[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6).

### The shared-source gap

Cards are inline-editable on the board, but the board's data lives in a **dedicated Kanban Markdown file** — a checklist document with a Kanban-specific structure — **not in the source notes' frontmatter.** There is no two-way sync between a card's column and a `status::` property elsewhere. Editing the board edits the board; it does not write back to a queryable property other views consume. The status is **positional and trapped in the board file**, which a table elsewhere cannot read or sort by.

**This is the structural difference from property-backed boards** (Projects, the Bases extension): the Kanban plugin's board is a self-contained document, not a view over a shared table.

### Popularity vs. the maintenance risk

The adoption figure sits in productive tension with the maintenance posture. The project's **MAINTAINERS document** states the code is fairly complex and asks that new maintainers be able to code without relying on LLMs[obsidian-kanban, MAINTAINERS.md](https://github.com/obsidian-community/obsidian-kanban/blob/main/MAINTAINERS.md). A GitHub issue, **"Is this project still maintained?"**, records the concern that without new maintainers the plugin risks incompatibility with newer Obsidian versions and accumulating bugs[obsidian-kanban, Issue #1157](https://github.com/obsidian-community/obsidian-kanban/issues/1157).

The causal chain runs from **code complexity → a high contributor bar → maintainer scarcity** → the seeking-maintainers condition. The mitigating factor is the **Markdown data model**: because boards are Markdown-backed[dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011), the documented incompatibility risk falls on the presentation layer rather than the stored text.

| Evaluation Axis | Kanban Verdict | Basis |
|---|---|---|
| Table / List | Not documented | board tool[dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011) |
| Kanban View | Strong pass | [dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011)[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) |
| Calendar View | Stack-only (via Full Calendar) | [Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6)[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) |
| Inline Edit / Shared Source | Split: edits yes, shared source no | [bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) |
| Data Portability | Pass — Markdown-backed | [dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011) |
| Maturity / Maintenance | Split: 913K installs, seeking maintainers | [dismantl, Obsidian community plugins by downloads, GitHub Gist](https://gist.github.com/dismantl/ad2de70c976dba6fdf0c3a7f72a83011)[obsidian-kanban, MAINTAINERS.md](https://github.com/obsidian-community/obsidian-kanban/blob/main/MAINTAINERS.md)[obsidian-kanban, Issue #1157](https://github.com/obsidian-community/obsidian-kanban/issues/1157) |

**Kanban is a depth-over-breadth plugin whose enormous footprint buys excellence on exactly one of the four views.** Adoption scale and view-type breadth are orthogonal; install count does not imply multi-view capability. Any table requirement a Kanban user develops is better met by adopting Obsidian Bases alongside the board.

## 10. Full Calendar

Full Calendar is a **single-view-type specialist** that renders one of Notion's four views at application-grade fidelity while deliberately ceding the other three. It **visualizes tasks on an interactive calendar using the FullCalendar JavaScript library**[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar), which models each event as a plain object supporting recurring events, drag-and-drop, resizing, and multiple views[FullCalendar, "Event Model — Docs"](https://fullcalendar.io/docs/event-model).

### Calendar depth, three deliberate gaps

- **Calendar** — its reason to exist and a decisive pass. Not a static month grid but a **manipulable surface** with month/week/day layouts, click-to-create, and drag-to-reschedule, all from the FullCalendar library's interaction idioms[FullCalendar, "Event Model — Docs"](https://fullcalendar.io/docs/event-model).
- **Table / Kanban / List** — **non-features by design.** A table comes from delegating to Bases["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/); a board comes from pairing with the Kanban plugin[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6); a list comes from Bases' native List["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/).

The documented integration pattern runs **Kanban + Full Calendar over a common note set**[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), so a task appears on a board and a calendar at once — the note is the shared substrate linking the views.

### Shared source and the write-back caveat

The strongest editing claim flows from the library's drag-and-resize behavior[FullCalendar, "Event Model — Docs"](https://fullcalendar.io/docs/event-model). The **open question** the cited evidence cannot settle is whether those gestures write back to each note's scheduling property — the two-way sync that separates a Shared Data Source from a read-only rendering. What is established is the integration topology: where tasks feed both Kanban and Full Calendar[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), the note links the views.

### The mobile-vault caveat

A load-bearing operational weakness shared by every frontmatter-reading plugin: Obsidian's **large-vault mobile indexing cost**. On Android, opening a vault of 50,000+ notes can take **~3 minutes to load and ~27 minutes to re-index** because IndexedDB transactions are not flushed to disk[Obsidian Forum, "Unpractical vault load time for large vaults on mobile"](https://forum.obsidian.md/t/unpractical-vault-load-time-for-large-vaults-on-mobile-indexeddb-transactions-are-not-flushed-to-disk/88470). This can delay when recently edited items render on a large mobile vault. The documented mitigation is the **Lazy Cached Vault Loader** plugin, which can reduce mobile start-up to ~2 seconds for vaults over 30,000 notes[d7sd6u, "obsidian-lazy-cached-vault-load," GitHub](https://github.com/d7sd6u/obsidian-lazy-cached-vault-load).

| Dimension | Full Calendar verdict |
|---|---|
| Table / Kanban / List | Not native; delegated to Bases / Kanban["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/)[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) |
| Calendar view | Native, interactive (library-backed)[FullCalendar, "Event Model — Docs"](https://fullcalendar.io/docs/event-model) |
| Inline editing | Library drag/resize; shared-source via note |
| Data Portability | Inherits frontmatter durability when note-sourced |
| Maturity | Mature library, community integration layer[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) |

**Full Calendar is the best-in-class implementation of one quadrant of the multi-view promise, deliberately ceding the other three to partner plugins.** Its value emerges only inside a Plugin Stack. By 2027, as the native Bases calendar path matures[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views), its defensible niche contracts toward interaction depth alone — the one dimension where a single-purpose specialist still outperforms a generalist's bolt-on tab.

## 11. Prisma Calendar and the Bases-Views Extension

The calendar/timeline tier splits along a **coupling axis**: Prisma reads any vault note's date directly and imposes no lock-in, while the obsidian-bases-views extension completes Bases' view matrix at the price of Bases dependency.

### Prisma Calendar

Prisma is a **schema-agnostic visualization layer**: where Full Calendar expects events in known shapes, Prisma reads whatever date a note already carries. A note with `Schedule:: 2026-01-15` appears on the timeline **requiring no predefined schema or specific field names** — `Schedule`, `due`, `date`, or any custom key works[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/).

- **Calendar** — Prisma's core competency, binding to arbitrary notes rather than structured events.
- **Table / Kanban / List** — none; Prisma is the temporal axis only, reaching multi-view parity solely inside a stack.

**Its strongest architectural claim:** because it reads frontmatter directly and stores no private index, a schedule change in the note propagates to the timeline without an intermediate store, mirroring the Bases shared-source model[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin)[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/). Data Portability is excellent — uninstalling Prisma leaves every note fully intact[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/).

The tradeoff is structural: **schema-agnosticism buys flexibility at the cost of enforced structure.** That resolves in Prisma's favour for already-messy vaults — it meets notes where they are instead of demanding a migration, delegating schema enforcement to Metadata Menu where wanted.

### obsidian-bases-views (Board/Gantt/Calendar Extension)

This extension is the bridge between Prisma's timeline focus and Bases' multi-view ambition: it adds **Board (Kanban), Gantt, and Calendar views to Obsidian Bases**[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views), extending the core's native Table and List["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/).

Because every added view sits on the Bases frontmatter source where edits in one view appear in others[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin), **Board, Gantt, and Calendar all inherit shared-source behaviour.** A card moved on the Board updates the note's frontmatter, which updates the Table row and Calendar placement. **Core Bases plus this extension covers all four prompt views plus Gantt — one of the most complete Four-View Coverage stacks in the survey.**

The tradeoff is **integration vs. independence**: the extension gains a unified config but is useless without Bases, whereas Prisma and the standalone Kanban plugin work without Bases at all. The choice resolves by audience.

## 12. Metadata Menu

Metadata Menu is documented as a **field-level metadata management companion** to database and view plugins, not a standalone renderer[Obsidian Plugins Guide, "Metadata Menu vs. Database Folder"](https://notes-automate.com/posts/comparing-obsidian-metadata-menu-vs-database-folder/). Its value is measured not by views it draws, but by the **typed, editable frontmatter properties** it contributes to views other plugins draw.

### Two functions

1. **Typed schema via File Classes** — File Classes enforce typed frontmatter fields, **preventing the typos that break Dataview queries** across thousands of notes[Obsidian Plugins Guide, "Explaining Obsidian Metadata Menu for Structured Data"](https://notes-automate.com/posts/explaining-obsidian-metadata-menu-for-structured-data/). A typed field yields consistent values, letting any query or view filter and group without fragmenting on typos.

2. **Inline editing of Dataview tables** — its core contribution. Metadata Menu adds context-menu items that **edit Dataview table fields directly inside the table**, turning a read-only rendering into an inline-editable interface[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/). A property edited through the context menu resolves to a frontmatter value — the same store Dataview reads and Bases renders[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin), making Metadata Menu a **Shared Data Source amplifier: one edit, many renderers.**

### Companion role and portability

The relational structure is the insight distinguishing this plugin from every renderer. The **two-plugin stack — Dataview for the view, Metadata Menu for the schema and edit — passes more of the Database Behavior criterion together than either alone**, because the edit verb Metadata Menu contributes[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/) is precisely the one a read-only Dataview table cannot perform.

Everything it governs remains **portable frontmatter** — the structured-data state travels with the note, unlike Database Folder's per-folder `database.md` config files[Obsidian Plugins Guide, "Metadata Menu vs. Database Folder"](https://notes-automate.com/posts/comparing-obsidian-metadata-menu-vs-database-folder/).

| Axis | Metadata Menu verdict | Basis |
|---|---|---|
| Table View | Editing layer only; no standalone table | [Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/) |
| Kanban / Calendar / List | None native; improves typed quality | [Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6)["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) |
| Inline Editing | Strong; core contribution | [Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/) |
| Portability | Strong; frontmatter-only | [Obsidian Plugins Guide, "Explaining Obsidian Metadata Menu for Structured Data"](https://notes-automate.com/posts/explaining-obsidian-metadata-menu-for-structured-data/) |

**Metadata Menu is not a renderer but the typed-schema and write-back layer that upgrades read-only renderers into editable ones.** It fails Four-View Coverage as a standalone tool, passes Data Portability strongly, and passes the edit portion of Database Behavior over a Dataview surface. Its forward relevance persists as long as the dominant renderers stay read-only — a territory that may shrink if native Bases views add their own typed-option editing.

## 13. Database Views and Proprietary-Format Plugins

Database Views (PlantBasedStudio) is the survey's clearest **proprietary-format** plugin, storing structured data in a self-contained **`.dbview` file** rather than distributing rows across Markdown notes. The trade at its centre: **typed-record convenience purchased at the price of Data Portability.**

### The record model

Each `.dbview` record carries **typed properties — text, numbers, select values with custom colours, and links to other notes**[PlantBasedStudio, "obsidian-database-views" README, GitHub](https://github.com/PlantBasedStudio/obsidian-database-views/blob/main/README.md). Type is fixed at the record level, removing the type-coercion ambiguity of frontmatter-derived tables. The **select-with-colours** type is the most Notion-reminiscent feature.

- **Table** — typed properties support a clean column-per-property layout.
- **List** — the model is list-shaped: a flat collection of typed records, each linking to a full note through an **eye icon**[PlantBasedStudio, "obsidian-database-views" README, GitHub](https://github.com/PlantBasedStudio/obsidian-database-views/blob/main/README.md), treating the record as an index over long-form content.
- **Kanban / Calendar** — **not documented.** No board grouping, no date-field binding[PlantBasedStudio, "obsidian-database-views" README, GitHub](https://github.com/PlantBasedStudio/obsidian-database-views/blob/main/README.md).

### The lock-in trade-off

This is the defining axis. **All data resides inside the `.dbview` file, and uninstalling the plugin renders that data inaccessible — vendor lock-in**[PanicVault, "KeePass vs. Proprietary Formats"](https://www.panicvault.org/keepass/vs-proprietary/). A proprietary format is controlled by its maintainer and may be only partially documented[PanicVault, "KeePass vs. Proprietary Formats"](https://www.panicvault.org/keepass/vs-proprietary/). The note-link property **partially** mitigates this — any linked note survives in Markdown — but the structured layer (typed properties, colours, relationships) does not.

The benefit and the lock-in are **two faces of the same design decision**: concentrating data in one proprietary container is what delivers the typed-record convenience. A user cannot have both the self-contained store's type guarantees and graph-wide Markdown durability.

### The extension-stack counterfactual

Against the proprietary route, **obsidian-bases-views** reaches comparable multi-view breadth (Board, Gantt, Calendar over Bases[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views)) while keeping data in Markdown frontmatter. **The same four-view ambition is achievable through a plain-text stack that incurs no lock-in.**

| Dimension | Database Views (`.dbview`) | obsidian-bases-views |
|---|---|---|
| Table | Typed records | Native via Bases core |
| Kanban / Calendar | Not documented | Added by extension |
| Data Portability | **Fail** — sealed `.dbview`[PanicVault, "KeePass vs. Proprietary Formats"](https://www.panicvault.org/keepass/vs-proprietary/) | **Pass** — Markdown frontmatter[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) |
| Shared Data Source | Single `.dbview` file | Shared Bases source |

Extension-stack architectures on the Bases core are positioned to absorb most structured-database demand, narrowing the defensible niche for any `.dbview`-style format to users who actively prefer a sealed store over graph integration.

## 15. View-Type Deep Dive: Table and List

Shifting from per-plugin profiles to per-view comparison: how well does each plugin render a Table or a List, judged on the database behaviors that make those views useful? The reference behavior is Notion's, where each database page is a row and every property is a **filterable, sortable, groupable column** reached through the column-header menu[Notion 2024, "Views, Filters, and Sorts"](https://www.notion.com/help/views-filters-and-sorts).

### Table view: two camps

Plugins divide into **GUI-managed point-and-click tables** with inline editing and **query-engine tables** rendering read-only output:

| Entity | Table behavior | Inline Edit | Shared Source | Notion-parity verdict |
|---|---|---|---|---|
| **Obsidian Bases** | Native, GUI-managed["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/)[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2) | Yes[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2) | Frontmatter, cross-view[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) | **Closest single-plugin match** |
| Dataview | Query-expressed, strong group/aggregate[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2) | Read-only[obsidian-dataview Discussion #748, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/748) | Lens over notes | Query depth, no edit |
| Datacore | API-defined, hierarchy-capable[blacksmithgu 2024, "Datacore List Views Documentation"](https://github.com/blacksmithgu/datacore/blob/master/docs/docs/code-views/list.md) | Editable (table) | Reads vault notes | Strong, beta |
| Obsidian Projects | No-code, basic sort/filter[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Yes (folder write)[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Folder of notes[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Fast dashboard, shallow query |

**The apparent paradox: the harder-to-write tool produces the more powerful table.** Dataview's grouping and aggregation are query-expressed, so they compose in ways a point-and-click menu cannot — the cheat sheet steers non-technical users to Bases instead, reserving group-by, sums, and counts for Dataview[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2). Bases wins **Inline Editing** decisively: a clickable table you edit inline (checkboxes, dates, selects) with point-and-click filters[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2), coupled to the shared frontmatter where an edit in one view appears instantly in others[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

### List view: the nesting test

The List view is judged on **nesting** (parent-child hierarchy) and **saved views**:

- **Datacore** is the clearest documented nesting primitive: `dc.List` supports explicit **grouping and hierarchies** across unordered, ordered, and block varieties[blacksmithgu 2024, "Datacore List Views Documentation"](https://github.com/blacksmithgu/datacore/blob/master/docs/docs/code-views/list.md). **Nesting is what separates a true List view from a flat enumeration** — the capability Notion's nestable list requires.
- **Bases** provides List natively["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) over an editable, shared frontmatter source[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin), reaching saved-view and editable-source parity.

So a List-heavy Notion replicator may need **both**: Datacore for parent-child hierarchy, Bases for the editable shared source. Neither single plugin yet documents both maximal nesting *and* editable saved views in one rendering.

### Comparative verdict

**No single plugin reproduces Notion's full Table-and-List experience, but Bases plus a query engine does** — the cheat sheet and Projects review both reach this complementarity conclusion independently[Lennart D. 2025, "Obsidian Cheat Sheet: Bases vs Dataview," Medium](https://medium.com/@lennart.dde/obsidian-cheat-sheet-bases-vs-dataview-225b08f5bcf2)[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/). On Database Behavior, Bases passes all four operations through its GUI while Dataview passes filtering and grouping but fails edit[obsidian-dataview Discussion #748, GitHub](https://github.com/blacksmithgu/obsidian-dataview/discussions/748). On Data Portability, the whole field scores well because every entity reads frontmatter or folder notes rather than a proprietary store, with Bases' frontmatter model the cleanest case[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

The residual gap to Notion is concentrated in two places: **query-expressed aggregation inside an editable view, and maximal list nesting inside a saved editable source.** Until either lands, **Bases leads on Table/List replication, and Notion-parity is a Plugin Stack rather than a single install.**

## 16. View-Type Deep Dive: Kanban and Calendar

Kanban and Calendar are where the field thins, because both demand more than tables do: a board must map a property to a column and let a drag rewrite that property; a calendar must bind notes to a date field and edit in place.

**Central finding: board and calendar replication splits the ecosystem into two camps — single-engine multi-view families that propagate edits across views, and bolt-on board/calendar plugins that render beautifully but read from a parallel source the table never sees.**

### The decisive architectural question

Does the board or calendar read the **same source the table reads**? Notion's bar: a board groups pages by any property, and dragging a card rewrites that property visibly everywhere[Notion Help Center, "Board view"](https://www.notion.com/help/boards).

| Entity | Board status source | Calendar date binding | Shared editable source across views |
|---|---|---|---|
| Kanban plugin | Board file position[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) | — | **No** — board file isolated |
| Obsidian Projects | Frontmatter property[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | Configured date field[Notes-Automate 2024, "Obsidian Projects Plugin Review"](https://notes-automate.com/posts/obsidian-projects-plugin-review-and-setup/) | **Yes** — four views over one folder |
| Bases + bases-views | Frontmatter via Bases[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) | Frontmatter date[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) | **Yes** — one Bases engine["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) |
| Full Calendar | — | Owned event source[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) | **No** — events not shared frontmatter |
| Prisma Calendar | — | Any frontmatter date[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/) | **Yes** — note is the source[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/) |
| bgarciamoura Notion Bases | Frontmatter property[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) | Frontmatter date[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) | **Yes** — edits propagate[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) |

### The central tension

**The best-feeling board and calendar in the ecosystem — the Kanban plugin and Full Calendar — are precisely the two that fail the Shared Data Source test.** The Kanban plugin's status lives in a board file, not a queryable frontmatter property; Full Calendar's events come from its own source, so an edit does not necessarily rewrite a `due::` property a separate board reads. Meanwhile the tools that pass (Projects, the Bases stack, bgarciamoura) lead with source unity rather than view-type polish.

**This resolves through composition.** Users who want Notion's drag-everywhere-edits-everywhere behaviour assemble a frontmatter-backed engine plus a **schema-agnostic calendar like Prisma**[Prisma Calendar documentation](https://real1tyy.github.io/Prisma-Calendar/), accepting slightly less calendar polish than Full Calendar in exchange for genuine cross-view sync — because the property-backed board writes to the same frontmatter the calendar reads.

Among single tools, the **bgarciamoura plugin's documented edits-appear-instantly-across-views behaviour is the nearest match**[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin), with board and calendar as views of the same frontmatter the table reads rather than bolted-on foreign sources.

The unresolved question: whether the single-engine families' interaction depth (recurrence, time-of-day granularity, in-view event editing) reaches the polish of dedicated specialists like Full Calendar's library-backed grid[FullCalendar, "Event Model — Docs"](https://fullcalendar.io/docs/event-model).

## 17. Plugin Stack Synergies and Combinations

No single plugin reproduces Notion's four views over one shared source with equal polish, so most users reach full coverage by assembling a **Plugin Stack**. Two dominate community practice.

### The two stacks

**Community stack: Dataview + Metadata Menu + Kanban + Full Calendar**
- Table/List from Dataview (made editable by Metadata Menu's context-menu editing[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/))
- Board from the Kanban plugin[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6)
- Calendar from Full Calendar[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar)
- **Cleanest synergy:** Table and List are both Dataview queries over one frontmatter, so they stay consistent by construction. The seam is the board and calendar, which read parallel sources.

**Integrated stack: Bases core + obsidian-bases-views**
- Table/List native from Bases core["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/)
- Board, Gantt, Calendar from the extension[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views)
- All views read **one shared frontmatter source** where edits propagate[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) — no board-table reconciliation needed.

| Maintenance axis | Community stack | Integrated stack |
|---|---|---|
| Shared source across views | Table/List share; board/calendar separate[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/)[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) | All views read one Bases source[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin)[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) |

### Conflicts and overhead

The tightest coupling is **Dataview–Metadata Menu**: because Metadata Menu's editable-table feature acts on Dataview's output[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/), the two are best treated as a unit kept compatible rather than independently upgradable. The **board is the principal source of sync overhead** in the community stack — keeping it consistent with the table requires a user-maintained convention[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), which the integrated Bases stack dissolves entirely. Config artefacts accumulate as a stack grows: DB Folder creates a `database.md` per folder[Obsidian Plugins Guide, "Metadata Menu vs. Database Folder"](https://notes-automate.com/posts/comparing-obsidian-metadata-menu-vs-database-folder/), whereas Metadata Menu keeps structure in typed frontmatter[Obsidian Plugins Guide, "Explaining Obsidian Metadata Menu for Structured Data"](https://notes-automate.com/posts/explaining-obsidian-metadata-menu-for-structured-data/).

### Single-plugin vs. stack decision framework

| User priority | Recommended configuration | Why |
|---|---|---|
| Table + List + editing only | Bases core + Metadata Menu typed fields | Native Table/List["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/); editing via typed frontmatter[Obsidian Plugins Guide, "Explaining Obsidian Metadata Menu for Structured Data"](https://notes-automate.com/posts/explaining-obsidian-metadata-menu-for-structured-data/) |
| All four views, tightest integration | Bases core + obsidian-bases-views | One shared source[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin); board/calendar as Bases views[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) |
| All four views, maximum query depth | Dataview + Metadata Menu + Kanban + Full Calendar | Dataview reach + inline edit[Obsidian Rocks, "Editing Dataview Tables with the Metadata Menu plugin"](https://obsidian.rocks/editing-dataview-tables-with-the-metadata-menu-plugin/); standalone board[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), calendar[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) |
| Standalone calendar focus | Full Calendar | Interactive calendar without a database stack[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar) |
| Maximum portability | Frontmatter-anchored stacks; avoid per-folder config files | Frontmatter stays readable[Obsidian Plugins Guide, "Explaining Obsidian Metadata Menu for Structured Data"](https://notes-automate.com/posts/explaining-obsidian-metadata-menu-for-structured-data/); avoids `database.md` clutter[Obsidian Plugins Guide, "Metadata Menu vs. Database Folder"](https://notes-automate.com/posts/comparing-obsidian-metadata-menu-vs-database-folder/) |

**Full coverage in Obsidian is a stacking problem governed by a single trade-off between source-sharing and plugin count.** The community stack buys query depth and portability at the cost of four maintenance surfaces and a manual board-table convention; the integrated Bases stack buys one shared source at the cost of a plugin-defined view config. **Neither dominates: the right stack is the shortest one whose native views meet the requirement, with extensions added only to close real gaps.**

## 18. Recommendations by Use Case

Choosing among the plugins is less about which is "best" and more about which views a workflow exercises. **The headline: Obsidian Bases plus its community view extensions is the default for most multi-view workflows, with specialist plugins winning only where polish on one view outweighs cross-view cohesion.**

### Project management and task tracking

A mature project workflow wants all four views at once: Table backlog, Kanban board, Calendar deadlines, List sub-tasks. **The Bases stack is the strongest pick.** Core Bases provides Table and List natively["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/); obsidian-bases-views adds Board, Gantt, Calendar[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views); and the **load-bearing advantage is that edits in one view instantly appear in others over one frontmatter source**[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) — exactly what a backlog-to-board-to-calendar flow needs.

The standalone Kanban plugin's cards do not participate in that shared store[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6), which is the core trade-off: the standalone board may feel more refined, but it does not auto-share data with a Bases calendar or table. **Because project tasks move constantly between states, shared-source edit propagation outweighs the standalone board's polish** — conditional only on both community repositories staying maintained.

### Content calendars and CRM

For an **editorial pipeline**, Full Calendar provides a library-grade publish-date spine[aviatesk, "obsidian-tasks-calendar," GitHub](https://github.com/aviatesk/obsidian-tasks-calendar), paired with the Kanban board for draft/review/publish stages[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) — focused, polished, but with cross-surface sync to validate rather than assume.

For a **CRM**, Bases is the pick: the repository advertises **relations and rollups** over frontmatter[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin), so a contact links to a company and a rollup sums open deals, with seventeen column types typing a deal value as a number and a stage as a select. All seven views share one source[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

**The paradox: the same portability that makes Obsidian attractive for CRM also blocks the email and marketing automation hosted stacks bundle**[SaaS Hunter, "SaaS Stacks 2026: Marketer's Tech Stack"](https://saashunter.pro/stacks) — automation generally requires the hosted backend portability rejects. The hosted route wins only where multi-user convenience outweighs local ownership.

### Research / PKM and lightweight lists

Research vaults weight **List generation and query expressiveness** over GUI editing. Core Bases List view["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) is the primary surface — a filtered, grouped list of sources whose typed frontmatter[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) edited in a table updates the list. For literature matrices, the native Table["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) encodes structured judgments while the list reads them back, never diverging because both draw on one source[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin).

**Anchor on the native List and Table views**["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) for durability — they are core, the most likely of any recommendation to remain stable across future releases. AI research assistants (ChatGPT, Claude, Gemini) sit **upstream**[Freistyle AI, "Free AI Tool Stack Picker"](https://freistyle.ai/tools/ai-tool-stack-recommender), helping draft material a researcher then files into a Bases list.

### Non-technical vs. power users

- **Non-technical default: Obsidian Bases (Core).** Native Table and List["Obsidian Bases: The Complete Guide to Database Views" 2026, got.md](https://got.md/obsidian-bases/) require no query language — the closest Obsidian comes to Notion's point-and-click database creation. Covers two of four views with zero configuration.

## 19. Limitations Relative to Notion

Obsidian can reproduce the *rendering styles* users associate with Notion, but the **relational behaviors** underneath still trail. The 2026 review notes the native SQLite architecture eliminates UI freezing[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/), narrowing but not closing the gap. Three durable deficits remain: **relations/rollups/formulas, editing and collaboration polish, and mobile performance at scale.**

### The relational ceiling is substrate-deep

The largest functional gap is **relational machinery**: typed links between records, aggregations across them, and column-level computation.

**Dataview** lists relational databases among the features it does not natively support[^23]: it cannot bind a stable, typed relation column whose integrity the engine maintains. It also lacks **column-level computation** like sums (only row-level)[obsidian-dataview Issue #575, GitHub](https://github.com/blacksmithgu/obsidian-dataview/issues/575), so rollup-style aggregation is doubly blocked — no native relation to aggregate over, no formula to do it. Users must resort to JavaScript[obsidian-dataview Issue #575, GitHub](https://github.com/blacksmithgu/obsidian-dataview/issues/575).

**This is a property of the storage substrate, not a missing feature:** plain Markdown carries no referential integrity. **Bases** attempts to express relational structure *inside* frontmatter — its repository advertises relations and rollups stored in plain Markdown[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) — and the SQLite backend edits thousands of entries without freezing[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/). If those advertised relations reach Notion's referential depth in practice (not yet independently audited), the filtered linked view moves toward delivery.

### Editing, collaboration, and mobile gaps

These usability deficits originate in **Obsidian's local-first architecture** rather than any single plugin:

- **Editing polish.** A 2026 comparison rates Notion five stars on ease of use against Obsidian's three["Notion vs Obsidian 2026," SmartProcessFlow](https://smartprocessflow.com/notion-vs-obsidian) — the difference between typed cell editors and frontmatter editing.
- **Collaboration.** Notion offers real-time, built-in collaboration; **Obsidian relies on Git or Obsidian Sync**["Notion vs Obsidian — devs' second brain 2026," toolchew](https://toolchew.com/en/notion-vs-obsidian/), so a shared board reflects a sync cycle rather than a live server edit.
- **Permissions.** Notion provides permission-controlled workspaces; Obsidian's local-first model has **no native permissions** beyond file-system access["Notion vs Obsidian for Teams 2026," StackFYI](https://www.stackfyi.com/guides/notion-vs-obsidian-for-teams-2026).
- **Mobile at scale.** The sharpest evidence: on Android, a 50,000+ note vault takes **~3 minutes to load and ~27 minutes to re-index**[Obsidian Forum, "Unpractical vault load time for large vaults on mobile"](https://forum.obsidian.md/t/unpractical-vault-load-time-for-large-vaults-on-mobile-indexeddb-transactions-are-not-flushed-to-disk/88470), mitigated only by a community caching plugin reducing start-up to ~2 seconds[d7sd6u, "obsidian-lazy-cached-vault-load," GitHub](https://github.com/d7sd6u/obsidian-lazy-cached-vault-load).

**These are not independent bugs but consequences of keeping data portable and local.** A Plugin Stack can close view-coverage gaps; it cannot, by adding plugins, close the collaboration gap rooted in architecture["Notion vs Obsidian for Teams 2026," StackFYI](https://www.stackfyi.com/guides/notion-vs-obsidian-for-teams-2026).

### Where the ecosystem is heading

Two trajectories with concrete evidence:

- **Datacore** targets **2–10× better query and rendering performance** plus fully interactable views["Datacore," blacksmithgu/datacore, GitHub](https://github.com/blacksmithgu/datacore/), with the Table marked complete and Card/Grouped views planned[blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md). Its weakness is stable-release readiness.
- **Bases**, backed by SQLite[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/), anchors the other trajectory. The likely near-term resolution between the two is **specialization, not convergence**: Bases covers the four core views with SQLite-backed editing, Datacore covers high-performance interactable table/list rendering for query-driven users.

| Scenario | View-Coverage | Performance | Collaboration |
|---|---|---|---|
| Base | Bases + extension cover four views[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) | SQLite removes table lag[Notes-Automate 2026, "Obsidian Bases Native Update Review 2026"](https://notes-automate.com/posts/obsidian-bases-native-update-review-2026/) | Sync-mediated only["Notion vs Obsidian — devs' second brain 2026," toolchew](https://toolchew.com/en/notion-vs-obsidian/) |
| Optimistic | Datacore adds board via Grouped cards[blacksmithgu/datacore ROADMAP 2024](https://github.com/blacksmithgu/datacore/blob/master/ROADMAP.md) | 2–10× gains realized["Datacore," blacksmithgu/datacore, GitHub](https://github.com/blacksmithgu/datacore/) | Sync-mediated only["Notion vs Obsidian — devs' second brain 2026," toolchew](https://toolchew.com/en/notion-vs-obsidian/) |
| Pessimistic | Kanban/Calendar stay community-dependent[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) | Mobile re-index latency persists[Obsidian Forum, "Unpractical vault load time for large vaults on mobile"](https://forum.obsidian.md/t/unpractical-vault-load-time-for-large-vaults-on-mobile-indexeddb-transactions-are-not-flushed-to-disk/88470) | Sync-mediated only["Notion vs Obsidian — devs' second brain 2026," toolchew](https://toolchew.com/en/notion-vs-obsidian/) |

**The collaboration column is invariant across scenarios — the central finding.** The trajectory is favorable on view coverage and editing performance but **fixed on collaboration and permissions**: a realistic adopter should expect a multi-view database matching Notion's views and portability while trailing on real-time co-editing through 2027.

## 20. Conclusion

**No single plugin fully replicates Notion, but the Obsidian Bases core paired with its companion-view extension comes materially closest to the Shared Data Source ideal**, with Dataview-class query engines and single-view specialists trailing on cross-view data unity.

**The structural claim the whole survey proves: replicating Notion in Obsidian is not a view-rendering problem but a shared-source problem.** Every category can render a Table, Board, or Calendar; only the Bases engine, on the evidence, edits one frontmatter store and reflects that edit across views[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin). Query engines render without editing; specialists edit within one view only. Stacks recover coverage[Geet Duggal, "Obsidian Kanban and Full Calendar Integration," Medium](https://medium.com/@geetduggal/tech-habits-obsidian-kanban-and-full-calendar-integration-a05a7ff2d2f6) at a maintenance cost — which is why the integrated Bases engine scores higher than a two-plugin patchwork.

### Final verdict

**Obsidian Bases paired with the bases-views companion reproduces Notion's shared-source, multi-view reflex closely enough to serve a single-user knowledge worker, holding a real Data Portability advantage through plain Markdown frontmatter**[bgarciamoura/obsidian-notion-bases-plugin, GitHub](https://github.com/bgarciamoura/obsidian-notion-bases-plugin) — while the companion renderers' community-maintained status[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views) is the one caveat keeping the match short of identical.

The **single most consequential near-term variable** is the stabilization of the companion Board and Calendar renderers on the Bases source, conditional on continued maintenance[AlexandrBukhtatyy, "obsidian-bases-views," GitHub](https://github.com/AlexandrBukhtatyy/obsidian-bases-views). By 2027, if that companion remains actively maintained, the match to Notion tightens; if it stalls, the four-view claim narrows back to the two views the core ships natively. The hosted SaaS route[Work with Opal, "Best marketing tools that integrate task management and calendars"](https://workwithopal.com/about/blog/best-marketing-tools-that-integrate-task-management-and-calendars/)[GoForStack, "Best For"](https://goforstack.io/best-for/) remains the alternative only where real-time collaboration outweighs the local ownership the frontmatter model uniquely delivers.

**One question remains unresolved:** whether the companion Board and Calendar views write back to the Bases frontmatter with the same fidelity as the core Table and List, or render read-only onto that source — the distinction that determines whether the shared-source match is complete or merely partial.
